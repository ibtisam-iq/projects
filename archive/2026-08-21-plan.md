# Tags & Tech Redesign: Design Doc

Status: **implemented.** Every phase below (§1–§12) has been built, verified in the
browser (desktop and mobile), and cross-checked against source repos. `README.md`,
`docs/architecture.md`, and `docs/authoring-guide.md` are kept in sync with this doc.
This is the working log of *why* things are the shape they are, not a pending proposal
anymore. Nothing here has been committed to git; it's all sitting in the working tree
per standing instruction (commits happen only when explicitly asked).

This doc exists because the change touches the data model (`data/projects.yaml`), the
build (`scripts/generate-projects.js`), and three UI surfaces (search, filters, card
rendering) at once. Landing it in one pass with no record of *why* would make it
unreviewable and unrepeatable. So: read, mark up, iterate, then I implement.

## 1. Where this comes from

A live bug (clicking the "Kubernetes" quick filter returned 1 project out of 8) led to
a full audit of `tech` and `tags` across all 8 projects, which surfaced real omissions
(tools named in the prose but missing from `tech`), one duplicate (`Route 53` vs.
`Amazon Route 53`), and a `tags` taxonomy with a couple of misplaced/redundant entries.
That audit is done and its findings are folded into §5 below , they don't need
re-litigating, they need executing once the model underneath them is fixed. Fixing the
data without fixing the model would just recreate the same drift the next time a
project is added.

You then raised six structural questions that are upstream of any of those fixes.
This doc answers each one, then proposes a concrete taxonomy, a single-source-of-truth
architecture, and a migration order.

## 2. The six questions

### Q1: Are Tags (Skills) and Tech (Technologies) the same thing, captured wrong? Or genuinely two things?

**Genuinely two things , your own example proves it.** You said: *"GitOps is a
category, an approach... and under this umbrella there may be plenty of tools like
ArgoCD, Flux."* That's the whole answer. **Tags = the discipline/domain** (GitOps,
CI/CD, Security, Observability...). **Tech = the concrete tool** that discipline was
practiced with (ArgoCD, Jenkins, Trivy, Prometheus...). They're not two views of the
same fact, they're two different altitudes: one is "what kind of work," the other is
"which specific product." A recruiter scanning skills wants the discipline list; a
recruiter scanning for a specific tool on their JD wants the tech list. Collapsing them
would lose one of those two scans.

**Recommendation: keep them separate, but make them share one spine.** Right now they
don't share anything , `tags` is free text, `tech` is free text, and nothing enforces
that a tag and the tech under it are even related. §4 proposes a taxonomy where every
`tech` entry is mapped to exactly one domain, and the domain list *is* the tag
vocabulary. So "GitOps" becomes both a selectable tag on a project *and* the category
header that groups ArgoCD/Flux/etc. in the tools popover , one taxonomy, two facets
reading from it.

### Q2: Should `tech` be unrestricted or capped to "recruiter-searched, daily-driver" tools?

Two different concerns got merged in how you phrased this, and they need different
answers:

- **Should the *data* be capped** (i.e., should `kubectx` simply not be recorded as a
  real thing DebugBox does)? **No.** If it's true, it's true. Deleting a true fact to
  make the list shorter is the "undercut my own work" failure mode you explicitly
  warned against , you'd be hiding real engineering effort (bundling and testing
  `kubectx`/`kubens`/`yq` inside 3 size-tiered images) to make a filter chip list
  tidier.
- **Should the *rendered chip row* be capped?** **Yes , this is Q3, not Q2**, see below.

So: no cap on what's recorded as true. A cap on what's *always visible* is a real,
separate, good idea.

### Q3: Should everything print, or should niche entries be filter/search-only background data?

**This is the right question, and I agree with your instinct.** A card currently
renders every `tech` entry as a chip (`ProjectCard.tsx:107-119`, no limit). DebugBox
alone has 10 tech entries once the missing ones from the audit are added, and that's
one line , `silverstack-cicd-platform` already has 11. A recruiter skims a card for
2-3 seconds; a wall of 10-11 chips is worse than the 5-6 that actually matter, because
the eye can't tell which ones are load-bearing.

**Recommendation:** split `tech` into "primary" (rendered on the card, the tools that
actually define the project at a glance) and the rest (still fully present in the data,
still fully searchable and filterable, just not chip-rendered on the card , visible
instead on the project's own detail page, where there's room and where a visitor who's
already interested wants the full picture). Concretely, order matters: keep authoring
`tech` in the YAML with the primary/headline tools first, and render only the first
N (I'd default N=6, tune per how it looks) as card chips, with a `+4 more` affordance
that links to the detail page rather than expanding inline. Filtering and search
continue to run against the *full* array regardless of what's rendered, so selecting
`kubectx` from the tools popover still correctly surfaces DebugBox even though
`kubectx` never appears as a chip on the card itself.

This also directly resolves your "does anyone care about kubectx" worry: it stops
competing for eye space on the card, but it's still true, still searchable, still
filterable, and still visible to anyone who opens the popover or the detail page and
specifically looks for it.

### Q4: Should the filter run against both Tags and Tech, and is the Search bar too narrow?

Two different mechanisms here, and they need opposite answers:

**The faceted dropdowns (Skills / Technologies) , keep them separate axes.** This
follows directly from Q1's answer. If tags and tech are genuinely different altitudes
(discipline vs. tool), merging their filter logic would mean selecting "GitOps" (a tag)
also matches a project that merely uses `Bash` scripts with no GitOps practice, because
some unrelated tag happened to share a word with a tech string , that's not narrowing,
that's noise. Faceted search's entire value is that each facet is a clean, independent
AND: category AND tags AND tech AND status AND year. That's already how
`App.tsx:28-54` is written, and it's correct. I'd keep it exactly as-is at the facet
level.

**The free-text Search bar , you're right, it's genuinely too narrow, and this is a
real bug, not a design question.** Current predicate (`App.tsx`):

```
project.title.toLowerCase().includes(q) ||
project.shortDescription.toLowerCase().includes(q) ||
project.tech.some((tech) => tech.toLowerCase().includes(q))
```

It doesn't check `tags`, doesn't check `description` (the long body, only the short
one), and doesn't check `sections`. Typing "ArgoCD Image Updater" , a real, load-bearing
detail that only appears in the long `description` and `sections`, not the short one ,
returns nothing. **Recommendation:** extend the predicate to search `title`,
`shortDescription`, `description`, `tags`, `tech`, and every `sections[].items[]`
string. This is a straightforward fix, low risk, no data model change required , I'd
land it independent of everything else in this doc.

### Q5: Are the current 4 tool-popover categories the right DevOps/SRE/Platform categories?

**No, and "Observability & Ingress" is the tell.** The current 4 buckets in
`toolCategories.ts` (`cloud-iac`, `cicd-security`, `observability-net`,
`os-runtimes-data`) were sized to hit a round number, not derived from how the
discipline is actually organized. Two symptoms: **Security got folded into CI/CD**
(`cicd-security`) even though Security is its own recognized category on every
DevOps/SRE/Platform JD you'll find, distinct from the pipeline that runs it. And
**Networking got folded into Observability** (`observability-net`) , a Gateway API
route and a Grafana dashboard have nothing to do with each other; they just both didn't
fit anywhere else in a 4-bucket budget.

There's no rule that says it must be 4 , the popover grid is
`sm:grid-cols-2 lg:grid-cols-4` (`ToolsMegaPopover.tsx:165`), which already wraps
cleanly to a second row if there are more than 4 groups. So the count should be
whatever the real taxonomy needs, not a number picked in advance. §4 proposes 6,
derived from what recruiters and JDs in this field actually scan for, with every one
of the 75 current tech strings assigned to exactly one.

### Q6: Are the Quick Filter presets the right 7?

Current: `Kubernetes, Amazon EKS, Terraform, ArgoCD, GitHub Actions, Jenkins, Docker`.
Once `Route 53`/`Amazon Route 53` are merged and the missing tech from the audit is
added, I'd pick presets by actual project coverage , a preset that matches 1 project
isn't "quick," it's a trap (that's exactly what happened with `Kubernetes`). Proposed
replacement, all verified against real per-project counts once §5's fixes land:
`Amazon EKS (4), Terraform (2), Docker (6), GitHub Actions (4), ArgoCD (1→ keep for
recognizability despite low count, it's a top-tier recruiter keyword), Trivy (3),
Kustomize (3)`. Swapping `Jenkins` (2 projects) for `Trivy` (3 projects, and a stronger
DevSecOps signal) and `Kubernetes` for `Amazon EKS`. Open to your read on this list ,
it's the easiest section to bikeshed and the cheapest to change later, so I wouldn't
block on it.

## 3. Single source of truth (the "or not" you flagged)

Today there is none. `toolCategories.ts` hand-maintains 4 `Set`s of tool names for UI
grouping only , nothing validates that `data/projects.yaml` only uses tools from that
set, nothing validates the `tags` vocabulary at all, and a typo or a near-duplicate
(`Route 53` vs `Amazon Route 53`) compiles silently.

**Proposal: one new file, `src/data/taxonomy.ts`, hand-authored, imported by both the
build step and the UI.**

```ts
// src/data/taxonomy.ts
export const DOMAINS = [
  { id: "cloud-iac",        tag: "iac",           label: "Cloud & Infrastructure as Code" },
  { id: "containers-orch",  tag: "kubernetes",    label: "Containers & Orchestration" },
  { id: "cicd-gitops",      tag: "ci-cd",         label: "CI/CD & GitOps" },
  { id: "security",         tag: "security",      label: "Security & DevSecOps" },
  { id: "observability",    tag: "observability", label: "Observability & Monitoring" },
  { id: "runtimes-data",    tag: ",",             label: "Runtimes, Languages & Data" },
] as const

// One entry per real tech string. The build fails if projects.yaml uses
// a string not listed here, or if two entries normalize to the same
// service (catches the Route 53 / Amazon Route 53 class of bug).
export const TECH_REGISTRY: Record<string, DomainId> = {
  "Terraform": "cloud-iac",
  "Amazon EKS": "containers-orch",
  "ArgoCD": "cicd-gitops",
  "Trivy": "security",
  "Prometheus": "observability",
  "Bash": "runtimes-data",
  // ...all ~80 entries, one line each, reviewable in a single diff
}

// Closed vocabulary. The build fails if projects.yaml uses a tag not
// listed here.
export const ALLOWED_TAGS = [
  "linux", "containerization", "kubernetes", "ci-cd", "gitops", "security",
  "devsecops", "iac", "networking", "observability", "autoscaling",
  "microservices",
  // trimmed per §5: automation, orchestration, cloud-native, aws dropped
] as const
```

- `scripts/generate-projects.js` imports `TECH_REGISTRY` and `ALLOWED_TAGS` and throws
  a build error naming the offending project + string if either check fails , the same
  posture as the existing per-route `og:url` build gate, so this is a familiar pattern
  in this codebase, not a new one.
- `toolCategories.ts` stops hand-maintaining its own `Set`s entirely; `getCategorizedTools`
  becomes a thin grouping over `TECH_REGISTRY` plus `DOMAINS`.
- A tool is added to the project the same day it's added to `TECH_REGISTRY` (one line,
  one place) , there's no second file to remember.

This is the direct answer to "must there be a single source of truth" , yes, and this
is the shape of it.

## 4. Proposed domain taxonomy (Q5, concrete)

Six domains, chosen to match how this field is actually organized on real JDs/resumes,
and specifically to stop lumping unrelated things together the way the current
`observability-net` and `cicd-security` buckets do:

| Domain | What it covers | Why it's separate |
|---|---|---|
| **Cloud & Infrastructure as Code** | AWS provisioning services (EC2, S3, RDS, CloudFront, Route 53, IAM*, KMS*...), Terraform, CloudFormation, eksctl | The "how the environment gets built" layer , distinct from what runs inside it |
| **Containers & Orchestration** | Docker, Kubernetes, Amazon EKS, kubeadm, Helm, Helmfile, Kustomize, Gateway API, AWS Load Balancer Controller, ALB Ingress Controller, ExternalDNS | Gateway API / Ingress / LB Controller are Kubernetes-native traffic resources , they belong with orchestration, not bolted onto Observability the way they are today |
| **CI/CD & GitOps** | Jenkins, GitHub Actions, ArgoCD, ArgoCD Image Updater, GHCR, Docker Hub, Nexus, Maven, npm, pytest, Webpack | The pipeline and delivery mechanism, kept separate from what the pipeline scans for |
| **Security & DevSecOps** | Trivy, SonarQube, Bandit, pip-audit, ESLint, Hadolint, JaCoCo, Cobertura, AWS IAM*, AWS KMS*, AWS CloudTrail* | Its own recognized category on every DevOps/SRE JD , was incorrectly folded into CI/CD before |
| **Observability & Monitoring** | Prometheus, Grafana, AlertManager, Elasticsearch, Filebeat, Kibana, Fluent Bit, CloudWatch | Now *only* monitoring/logging tools , no more unrelated networking sharing the bucket |
| **Runtimes, Languages & Data** | Java/Spring Boot, Python/Flask, Node.js/Express, React, Bash, systemd, Alpine/Ubuntu, PostgreSQL/MySQL/DynamoDB, RabbitMQ/Redis/SQS/SNS/Lambda, Nginx, Cloudflare(+Tunnel), MkDocs | Catch-all for the application/runtime/data layer and edge-adjacent tools that don't belong to a provisioning or delivery pipeline |

\* IAM/KMS/CloudTrail are AWS services but their *purpose* in every project they
appear in is security/audit, not provisioning , I've placed them in Security &
DevSecOps rather than Cloud & IaC. This is the one placement in the table I'd flag as
a genuine judgment call, not an obvious fact , happy to move them if you read it
differently.

**DECISION NEEDED:** does this 6-domain split read right to you, or would you rather
see Networking pulled back out as its own 7th bucket? I chose to distribute it (K8s
routing → Containers & Orchestration, cloud DNS/CDN → Runtimes/Data) specifically to
avoid recreating an "ingress"-shaped grab-bag, but a dedicated Networking domain is a
legitimate alternative if you want traffic/delivery to stand on its own the way
Security now does.

### Domain ↔ Tag mapping

Each domain also becomes a tag (except Runtimes/Languages, which is too broad to be a
meaningful "skill" a recruiter filters by , nobody searches "I want a candidate who
knows a runtime"). So the tag vocabulary becomes the 5 domain tags, plus tags that
describe *how* something was done rather than *what category of tool* , these don't
map 1:1 to a domain and stay as their own concepts: `gitops` (a practice, sits logically
under CI/CD but is worth its own tag since it's a distinct hiring keyword),
`autoscaling`, `microservices`, `devsecops` (the practice, distinct from the `security`
tools domain), `linux`.

Final `ALLOWED_TAGS` (12, down from the current 17):

```
iac, kubernetes, ci-cd, gitops, security, devsecops,
observability, networking, autoscaling, microservices,
containerization, linux
```

Dropped from the current 17, per the audit in §5: `automation` (redundant with
`ci-cd`/`iac`), `orchestration` (redundant with `kubernetes`), `cloud-native` (too
vague to distinguish anything), `aws` (inconsistently applied , see §5), `documentation`
(on the wrong project, and thin as a standalone skill for one entry).

**DECISION NEEDED:** confirm the drop list, especially `aws` , if you want it kept,
the right fix per §5's finding is to apply it consistently to every AWS-heavy project,
not just `java-monolith`.

## 8. Phase 2: closing the gaps Q3 opened

Landing Q3 (cap card chips, curate the rest) surfaced three follow-on gaps, raised
directly and fixed the same day:

1. **No file taught a future author , human or LLM , the actual contract for a new
   `data/projects.yaml` entry.** `docs/architecture.md` documented the schema shape but
   not the taxonomy rules (`tech`/`tags` must be registered in `taxonomy.ts`) or the
   ordering rule below. **Fixed:** new [`docs/authoring-guide.md`](./docs/authoring-guide.md)
   , schema, taxonomy rules, the ordering contract, and a checklist, written to be handed
   to an LLM as-is. Linked from the YAML file's own header comment, since that's the
   first thing an author reads, not just from README/architecture.md.
2. **The "first N renders" rule was implemented but never documented or explicit.** A
   real gap , `ProjectCard.tsx` sliced the array; nothing said the slice point was a
   contract an author needs to actively write for. **Fixed:** documented in the YAML
   header, in `authoring-guide.md#ordering-tech`, and in the `VISIBLE_TECH_COUNT`
   comment itself. There's no automated check for ordering *quality* (which tools are
   "most representative" is a judgment call, not a mechanical property) , the guide says
   so explicitly rather than implying a check exists where none does.
3. **N=6 was reconsidered and changed to 8.** Re-auditing all 8 projects against their
   own top-6 selections found real signal being cut, not noise ,
   `microservices-demo`'s top 6 excluded `Prometheus`/`Trivy` despite Observability and
   security scanning being headline sections; `retail-store-sample-app`'s excluded
   `Lambda`/`DynamoDB` despite the serverless event pipeline being one of its four
   sections; most seriously, `polyglot-monolith-deployment`'s top 6 was 100%
   infrastructure tools (`Kubernetes`, `Amazon EKS`, `kubeadm`, `AWS EC2`, `Amazon ECS`,
   `Amazon RDS`) with zero languages visible, despite the project's entire premise being
   three languages across four compute models. Went to 8 and rebalanced every project's
   `tech:` order against its own description so the visible set leads with what the
   project is *about*, not just what was mechanically first after the earlier data-fix
   edits. `debugbox` , the project that started this whole thread (`kubectx` visible,
   "does anyone care") , now shows `Docker (Buildx & QEMU), Alpine Linux, Trivy,
   Hadolint, GitHub Actions, kubectx, kubens, yq`: the build-quality tools plus the
   actual bundled K8s-debugging payload, with `Bash`/`Make`/registries pushed to the
   overflow.

Verified: `npm run build` and `npm run lint` clean; the new `tech:` order spot-checked
live in the browser against the rendered card chips for `debugbox`,
`microservices-demo`, and `polyglot-monolith-deployment`.

## 9. Phase 3: popover layout after the domain count grew

Going from 4 to 6 domains (§8) had a UI side effect nobody had checked: the
Technologies popover used a fixed `lg:grid-cols-4`, so 6 domains wrapped as an uneven
4-then-2 row, and each column's tool list was capped at `max-h-64` (256px) , together
that pushed the popover to roughly full-viewport height.

**Fixed two things in [`ToolsMegaPopover.tsx`](./src/components/ToolsMegaPopover.tsx):**

- Column count is now derived from domain count via a small literal lookup map
  (`GRID_COLS_BY_DOMAIN_COUNT`), keeping the grid at ~2 rows instead of a fixed 4
  columns , 6 domains now render 3-and-3, matching what a symmetric 2-row layout
  needs. The map already covers up to 8 domains, so a future domain added to
  `taxonomy.ts` doesn't silently regress the layout the way the fixed `4` did.
- Per-column tool list height dropped from `max-h-64` (256px) to `max-h-40` (160px),
  and the popover's own outer cap from `60vh` to `50vh`. The Skills dropdown in
  `TopFilterBar.tsx` was shrunk to match (`max-h-60` → `max-h-40`), so the two
  popovers read as one consistent, shrunk design language rather than two
  differently-sized boxes.

Verified: popover height dropped from ~800px (near full-viewport) to a
viewport-capped ~552px maximum at any window height, 3-column grid confirmed via
computed `grid-template-columns`. `npm run build` and `npm run lint` clean. Row count
per column was tuned further afterward (5 → 4 → 3, both dropdowns pixel-matched each
time); landed on 3, confirmed by direct request after weighing it against 2 (2 would
make the popover unbrowsable without scrolling for nearly every domain).

## 10. Phase 4: auditing tech/tags against the actual source repos

Everything through §9 audited the YAML's `tech`/`tags` against the YAML's own prose
(`description`, `sections`). That's necessary but not sufficient , prose can be as
wrong as the data it's supposed to justify. This phase audits against the real
source repository instead: every Dockerfile, script, config, README, and CI workflow,
not just what the project's own description claims about itself.

**Methodology:** for each project, read the actual repo path (provided per-project,
since these are separate local repos this one doesn't have access to by default),
confirm which scripts genuinely execute at build/deploy time versus which are
optional/reference/dead code, and cross-check the resulting tool list against
`tech`/`tags`.

**`silverstack-cicd-platform` , audited, zero changes.** Read all of
`silver-stack/iximiuz/rootfs/` (5 image dirs + base) and all 7 GitHub Actions
workflows. Confirmed: every one of the 12 current `tech` entries is genuinely used;
nothing to remove. Nearly added ~34 tools from `dev/machine/install-tools.sh`
(confirmed running at build time , kubectl, Helm, Terraform, Trivy, eksctl, eight
more) before catching the real distinction:

**The rule this surfaced, now in [`docs/authoring-guide.md`](./docs/authoring-guide.md#tech):
"genuinely used to build this project" excludes a tool that's merely pre-installed in
a personal dev-machine/workstation image, even when that image is itself a real,
shipped part of the project.** `dev/machine` is one of SilverStack's 5 real images, and
its ~34 bundled CLI tools are real , but they're facts about a daily-driver workstation
loaded for general convenience, not facts about what SilverStack's own engineering work
required. Maven is the clean test case: it already correctly lives in `tech` for
`java-monolith` and `devsecops-pipeline-engineering`, where a Maven build genuinely
runs. It does not belong in `silverstack-cicd-platform`'s `tech` just because Maven
happens to be pre-installed in that project's dev-machine image. Also confirmed
`install-tools-all.sh` (~350 more tools) is dead reference code, never invoked by any
Dockerfile , correctly already excluded.

**`microservices-demo` , audited, 3 additions, zero removals.** Scope was deliberately
narrower here: the app is a fork of Google's Online Boutique the user didn't write, so
per instruction I read only the fork's `README.md` + the 3 linked GitHub Actions
workflows, then went deep on the CD repo (`platform-engineering-systems/systems/
microservices-demo`) , excluding its nested `app/`, which is the same upstream fork
checked out a second time, not the user's work either. All 23 existing `tech`/`tags`
entries confirmed accurate. Found the CD repo carries **two Terraform variants**
(`eks-aws`, `eks-kodekloud`), and the one the project's own "Proof of Deployment"
section documents as actually deployed (matches the KodeKloud SCP story already in the
description) provisions self-managed nodes via **CloudFormation**, with explicit
**AWS IAM** roles (`iam-eks.tf`) forced by SCP `iam:PassRole` restrictions, plus a
bastion **AWS EC2** instance already named in the description but never in `tech`. All
three added , genuinely used to build the deployed infrastructure, not incidental.
(Also surfaced, but out of scope to fix: the CD repo's own `README.md` claims ECR +
Cloud Build + Fluentd, while its actual configs use GHCR + Filebeat only , this
portfolio's `tech` list is already correct on this point, no change needed.)

**`retail-store-sample-app` , audited, 1 correction + 4 additions.** README states plainly
that both the base Helm charts and the Terraform modules (`terraform/eks|ecs|apprunner/`)
are upstream AWS Containers team work , the user's own contribution is the
`values-*.yaml` overrides, the 3 Helmfile configs, and execution/validation. Read the
README, the `helmfile-eks.yaml` + Helmfile README (both linked), and
`values-alb-ingress.yaml` (linked, confirms `alb.ingress.kubernetes.io/*` annotations
and `className: "alb"`).

Found an internal contradiction already in the YAML: `sections` said "Deployed the
